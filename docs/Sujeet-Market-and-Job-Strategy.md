## Concrete stack decision

Use **Python + SQL + PySpark + Databricks/Delta Lake + AWS** as the default learning route. Existing approved access to another cloud may justify changing the cloud while retaining the same architecture concepts.

Start locally with Python, Git, PostgreSQL, containers and tests. Retain Oracle as a source only where a legitimate development environment is available. Learn AWS identity, storage, networking and monitoring before managed processing. Develop Spark concepts locally, then validate one deployment on the selected platform with a defined budget.

Choose one scheduler in depth. Implement transformations, data tests and business definitions with dbt where it fits. Use Kafka for a focused streaming exercise rather than making every pipeline real time. Add API development, pgvector, model APIs, evaluation and a versioned Python library when the base pipeline is reliable.

Treat Snowflake/Fabric, additional clouds and extra agent frameworks as role-specific branches. Do not pursue deep proficiency in all platforms at once. Evaluate the stack choice after a fresh sample of ten suitable target roles, recording mandatory versus preferred requirements and actual experience constraints.

## Job-readiness stages

**Months 1–3:** Foundational Python and software engineering. Finish the 90-day pipeline milestone and document existing Oracle achievements. Use 15–20 hours/week; do not claim Python expertise at this point.

**Months 4–6:** Seek a bounded internal modernization/pipeline project or a hybrid SQL/Python opportunity if the practical gates pass. Start interview practice and targeted role conversations. Employer access, willingness and seniority alignment still need to be established.

**Months 6–9:** Assess readiness for broader data-engineering interviews using demonstrated Python, Spark, cloud, modelling and recovery evidence. Prioritize roles that value his financial-services experience and allow the new-stack experience he can honestly show. This is a readiness review, not an offer deadline.

**Months 9–15:** Add evaluated AI retrieval, controlled APIs, deployment and reliability. Expand toward data/AI platform opportunities once he can explain production trade-offs and demonstrate failures and recovery.

**Months 18–24 and beyond:** Deepen Python, architecture review, reusable frameworks and operational leadership. Use sustained evidence for principal/architect positioning.

## Practical interview preparation

From month 4, use one or two weekly sessions within the study budget:

- Python coding: collections, complexity, iterators, file/API processing, errors, testable design and debugging. Add appropriate algorithm practice for the actual interview format.
- SQL: window functions, joins, nulls, reconciliation, dimensional modelling and execution-plan reasoning.
- Spark: partitioning, shuffles, joins/skew, memory, file layout, correctness and restart behavior.
- System design: ingest trades, reconcile changes, publish analytics and serve controlled AI answers under stated constraints.
- Operations: explain a measured incident, recovery drill, performance improvement and cost trade-off.
- Leadership: prepare six truthful stories covering ownership, disagreement, ambiguity, mentoring, incident response and business outcomes.

Pass two independent mock interviews with different exercises before claiming interview readiness. Ask reviewers to identify the weakest evidence, then fix it. A course completion or certificate does not substitute for the practical gate.

## Positioning and offer quality

His strongest positioning is an experienced financial-services database engineer who has demonstrated modern data-platform delivery. Use “learning” or “project experience” accurately for new skills until they become professional experience. Keep the VP employment title but explain actual scope.

Prepare three short case studies: a reconciled migration, a performance/reliability improvement and an evaluated AI investigation assistant. Each should show the problem, alternatives, implementation, failures, measured results and personal ownership.

For each prospective offer, compare role scope, coding/architecture ownership, team quality, data scale, platform maturity, on-call expectations, location, fixed pay, variable pay, equity terms and growth opportunities. The sampled postings do not establish a defensible compensation range. Salary benchmarking should use the actual location, level and offer structure when those are known.

Begin targeted applications once the relevant gates pass; do not wait for every advanced topic. Track interview feedback and adjust the next month's work. No applications or messages have been sent as part of this research.
